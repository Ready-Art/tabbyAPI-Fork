# ReadyArt ExLlamaV2 Fork (TP / MTP / FlashInfer)

Public repos: **[Ready-Art/tabbyAPI-Fork](https://github.com/Ready-Art/tabbyAPI-Fork)** (this integration,
branch `ReadyArt`) and **[Ready-Art/exllamav2-Fork](https://github.com/Ready-Art/exllamav2-Fork)**
(the fork).

TabbyAPI's `ReadyArt` branch supports the
[ReadyArt ExLlamaV2 fork](https://github.com/Ready-Art/exllamav2-Fork), which adds
tensor-parallel and MTP speculative-decoding paths on top of exllamav2 0.3.2.
The fork is built and tested on **SM86 (Ampere, RTX 3090)** and requires
**flashinfer-python >= 0.7.4** plus **Flash-Attention 2 (required for now, even with FlashInfer)**.

> **Development focus & testing environment.** The majority of the work has gone into the
> **MP + CUDA graphs + MTP path**, including a custom PCIe P2P collective kernel for the small
> decode/verify collectives. It is tested on **4× RTX 3090 (sm86) on a PCI switch with P2P enabled**,
> launched with:
>
> ```bash
> NCCL_P2P_LEVEL=PXB python main.py
> ```
>
> `NCCL_P2P_LEVEL=PXB` enables PCIe peer-to-peer across the PCI switch on the tested rig; **the
> right value depends on your topology** (`PXB`/`PHB`/`SYS`/`NODE`; not needed on NVLink). The fork's
> P2P kernel probes `canAccessPeer` and falls back to NCCL automatically if peer access is unavailable.
>
> The tested 3090s are **power-limited to 200 W each via [LACT](https://github.com/ilya-zlobintsev/LACT)**
> (stock TDP 350 W). **Performance will be significantly better on full-powered GPUs** — every number
> reported for this fork is a 200 W-cap lower bound, not the hardware's ceiling.
>
> **Other configurations work but are not the priority.** `sp`, the `native` paged backend, non-MTP
> decoding, other architectures and other model families are functional but receive far less
> optimization effort and **will not match the performance of the MP + CUDA graphs + MTP path** on
> the tested rig. Only Gemma-4-31B-IT has been tested end-to-end.
>
> **Feedback & contributions:** want a change? Open a
> [GitHub issue](https://github.com/Ready-Art/exllamav2-Fork/issues) (or on
> [this repo](https://github.com/Ready-Art/tabbyAPI-Fork/issues) for the API integration).
> **Pull requests are welcome** — open a PR against the `ReadyArt` branch describing what and why.

Install the fork from source against your Torch build (tested: Python 3.12.15, torch 2.15.0+cu132,
CUDA toolkit 13.5 with `nvcc` on `PATH`):

```bash
# uv manages Python 3.12 itself (https://docs.astral.sh/uv/getting-started/installation/)
uv python install 3.12
uv venv venv --python 3.12 && source venv/bin/activate

# torch first — the fork's setup.py compiles its CUDA extension against the installed torch
uv pip install torch==2.15.0+cu132 --index-url https://download.pytorch.org/whl/cu132

git clone https://github.com/Ready-Art/exllamav2-Fork
cd exllamav2-Fork
uv pip install -r requirements.txt
TORCH_CUDA_ARCH_LIST="8.6" uv pip install -e . --no-build-isolation
flashinfer download-kernels

# Flash-Attention 2 — required for now even with FlashInfer (TP / dynamic-generator paths).
# Wheel for Python 3.12 / torch 2.15 / CUDA 13.2; other combinations:
# https://github.com/mjun0812/flash-attention-prebuild-wheels/releases
uv pip install "https://github.com/mjun0812/flash-attention-prebuild-wheels/releases/download/v1.5.0/flash_attn-2.8.3+cu132torch2.15-cp312-cp312-linux_x86_64.whl"
```

Source installs are detected automatically and are allowed with CUDA 13 Torch
(prebuilt upstream wheels are CUDA 12 only).

**CUDA allocator:** the fork TP backends (`sp`/`mp`) force PyTorch's **native**
caching allocator. `cudaMallocAsync` corrupts the fork's whole-step CUDA-graph
replay (token-level garbage under sampling) and breaks MP's IPC worker pipes, so
TabbyAPI overrides `PYTORCH_CUDA_ALLOC_CONF` to `backend:native` for these backends
even if it is preset in your environment. No action needed; do not force
`cudaMallocAsync` back on for the fork TP path.

## EXL2.5 quantization format

The fork's **EXL2.5** format (uniform-bit fast-path GEMM + optional Hadamard/AWQ
quality upgrades) is supported transparently: the format tags are self-describing
in the safetensors, so an EXL2.5 checkpoint loads with **no config switch** — set
`model_name` to its directory like any EXL2 model. Requirements and rules:

- The **exllamav2 fork CUDA extension must be built from the `ReadyArt` branch**
  (the fast-path kernels live there). After updating the fork, rebuild it
  (`TORCH_CUDA_ARCH_LIST="8.6" uv pip install -e . --no-build-isolation`) and
  restart the server — a running server keeps the old extension until restarted.
- **EXL2.5 features require the EXL2.5 fast path.** Tensors converted with
  `-x25u` (uniform bits) are served by the new kernel; classic mixed-bpw EXL2
  tensors run on the original kernel unchanged, and both kinds can coexist in one
  model. Hadamard/AWQ tensors always use the fast path (the loader aborts loudly
  rather than run them on the legacy kernel, which cannot apply their activation
  transforms). `EXL2_EXL25=0` is an A/B kill switch for *plain uniform* tensors
  only — it cannot disable had/awq tensors, and it is not a fix for a broken
  checkpoint.
- **Hadamard conversions use `-hb 16`** (fp16 head); with a quantized head the
  converter skips Hadamard on the lm_head.
- Convert with the fork's `convert.py` (`-x25u 6 -x25h -x25a` for the quality
  preset). Use a fresh work dir per job; several conversions can run in parallel
  on separate GPUs from one venv. See
  [doc/convert.md](https://github.com/Ready-Art/exllamav2-Fork/blob/ReadyArt/doc/convert.md)
  and the [EXL2.5 section of the exllamav2-Fork README](https://github.com/Ready-Art/exllamav2-Fork#exl25-quantization-format).
- **Status (2026-11-23, user-confirmed coherent on MP + MTP):** kernel/format
  parity, graph capture, MoE and engram tests all pass; real-weight reconstruction
  verified on both runtime paths at m=1/4/16 with zero NaN/inf. The Hadamard
  activation rotation and the fast-lane dot partials accumulate in fp32 (fp16
  intermediates overflowed on large-magnitude activation probes — a latent risk;
  m=8/16 throughput regressed and is the next tuning target). The converter's
  Hessian rotation/AWQ propagation were fixed. **TP loader fix:** the MP/TP
  loaders freed the AWQ scale while the QMatrix kept a raw pointer to it
  (gibberish + zero acceptance); all TP construction paths now retain it — a
  freshly converted checkpoint runs coherent on MP + MTP (user-confirmed
  2026-11-23). **The first checkpoint is invalid**: its conversion was
  interrupted and resumed with a corrupted calibration trajectory — always
  re-convert with a fresh work dir; treat EXL2.5 checkpoints converted before
  2026-11-22 as invalid. Throughput A/B vs EXL2-6.0 still being measured.

## Tensor-parallel backends

`model.tensor_parallel_backend` selects the TP implementation:

| Value    | Backend                                                         |
|----------|-----------------------------------------------------------------|
| `native` | Upstream-style TP with the paged dynamic generator (batching).  |
| `sp`     | Fork single-process TP, streaming generator, batch size 1.      |
| `mp`     | Fork multiprocess TP: one worker process per GPU. Batch size 1, or **experimental multi-batch with MTP** (see below). |
| `nccl`   | Alias for `mp` on exllamav2.                                    |

**Sliding-window models (Gemma-4) must use `sp` or `mp`**: the paged TP
attention kernel has no sliding-window support. When `native` is requested for
an SWA model with TP, TabbyAPI automatically switches to `sp` and logs a
warning. Non-TP loads (single GPU / autosplit) of SWA models also use the
streaming path (batch size 1, fresh prefill per job) with the fork's
`ExLlamaV2Cache_SWA` ring cache — the paged dynamic generator's SWA ring
protocol is not verified in this integration. Non-SWA models keep the paged
dynamic generator with batching on every load mode.

The fork TP paths run **one job at a time** (`max_batch_size` forced to 1) on
`sp` and on `mp` **without** MTP. With `mp` + MTP, `max_batch_size` is honored as
an **experimental** multi-batch opt-in (default 1 — see below). CFG, vision input
and (for `mp`) LoRAs are not supported on these paths; requests using them are
rejected or fall back with a warning.

**GPU count:** `gpu_split` may list **2, 3 or 4 GPUs** (validated for Gemma-4-31B;
the KV heads split unevenly, e.g. 3 GPUs → full-attention kv 2/1/1, sliding kv
6/5/5). **5+ GPUs are not supported for Gemma-4**: its full-attention layers have
only 4 KV heads, so a fifth rank would hold zero heads and the attention path has
no KV-head replication. Models with ≥ `world_size` KV heads on every layer can use
5+. See the exllamav2-Fork README ("GPU count") for the split/gather details.

### Multi-batch (experimental, MP + MTP)

**Status: experimental.** Validated on the tested 4× RTX 3090 rig under true
concurrent load at `max_batch_size: 4` (mixed context lengths, greedy and
sampled, shared-prefix cloning, per-slot continuations). Leave
`max_batch_size` unset (or 1) for the single-job behavior.

```yml
model:
  tensor_parallel_backend: mp
  draft_model:
    draft_mode: mtp          # multi-batch requires MTP
  max_batch_size: 4          # experimental; VRAM scales per concurrent slot
  cache_size: 32768          # per-slot depth; reduce for more slots / fewer GPUs
```

How it works:

- Each concurrent job owns one **cache row (slot)**. Verify rounds are batched
  CUDA graphs (`(B, W+1)` rows, one graph per batch size) with per-row
  acceptance, rewind and sampling — every emitted token still comes from the
  target's verified logits. Each scheduler step drains every active row's
  decided tokens (a small burst of chunks), so rounds always run at the full
  active batch size instead of desynchronizing into solo rounds.
- **Per-slot prompt caching**: a continuation reuses a slot's K/V when its
  prompt strictly extends that slot's own history, restores its prompt-boundary
  ring snapshot, or shares a long prefix with it (`prompt cache partial reuse`:
  edited/regenerated turns rewind to the divergence point — a position
  truncation, no copies); otherwise the row is reset.
- **Shared-prefix cloning**: a new job that shares a long prefix with another
  slot's lineage (same system prompt / few-shot / document, or a continuation
  whose own slot is still busy) copies that slot's committed K/V instead of
  re-prefilling the prefix. Copies, never aliases — slots cannot
  cross-contaminate each other's cache. Logged as
  `MP MTP prompt cache clone (slot r <- slot i): reusing N shared-prefix tokens`.
  `EXL2_BATCH_KV_CLONE=0` disables; `EXL2_BATCH_CLONE_MIN` (default 512) sets
  the minimum prefix length worth cloning.
- The **sparse draft head** (`draft_model.sparse_draft_head`) and the
  **whole-window draft CUDA graph** (`draft_model.mtp_draft_graph: true` /
  `EXL2_MTP_DRAFT_GRAPH=1`) both work on the batch path.
- Prefill is serialized per slot, chunked, with decode rounds for already-active
  jobs interleaved between chunks (an active job stalls at most one chunk while
  a new prompt prefills).
- Requests with sampling **filters or banned strings** are not MTP-eligible:
  they wait for the active batch to drain, then run solo on their own row.
- Generation is automatically capped so the verify window always fits inside
  the cache depth (`max_seq_len − prompt − draft window`); a logged
  `capping max_new_tokens` line means the request asked for more tokens than
  the remaining cache could hold.
- Server log every 50 rounds: `[mtp-mp-batch] … acc/round … emit/round …
  ms/round (gather/draft/verify/accept/rewind) … draft_agree …`. Judge batching
  speed by **total** tokens/s across streams (per-stream rates divide that by
  the number of active jobs). Measured ~85–110 tok/s aggregate across 4
  concurrent streams on open-ended essay prompts at temperature 0.7
  (4× RTX 3090, W=3, `cache_size: 32768`); acceptance-dependent.

VRAM: the KV cache and the MTP K/V shadow are allocated **per slot**
(~5 GB/slot at 160k context for Gemma-4-31B on 4 GPUs, ~1.2 GB/slot at 32k).
On 24 GB cards, `max_batch_size: 4` fits with `cache_size: 32768` on 4 GPUs
(master ~18.5 GB including the draft graph's GPU embed table). **On 2 GPUs
each rank holds twice the KV heads** — halve the per-slot budget again
(e.g. `cache_size: 8192–16384` for batch 4) and/or use a lower-bpw quant
(6.0 bpw weights alone are ~11.7 GB/rank on 2 GPUs; 4 bpw is the realistic
2-GPU choice).

### Prompt-cache RAM offload (experimental, MP + MTP)

**Status: experimental.** Opt-in tiering of idle prompt-cache lineages to host
RAM, so the VRAM context budget is not a hard cap on how many conversations stay
cached — useful when sharing the API across several users/conversations. Works on
both the single-job (`max_batch_size: 1`) and multi-batch MP + MTP paths. DFlash
is not supported (it keeps its own draft K/V); the option is ignored there.

```yml
model:
  tensor_parallel_backend: mp
  draft_model:
    draft_mode: mtp
  max_batch_size: 4                 # 1 or more
  prompt_cache_offload: true        # opt-in (default false)
  prompt_cache_ram_limit_mb: 16384  # host-RAM cap for cold lineages (default 8192)
```

How it works:

- The VRAM tier is the `max_batch_size` preallocated cache rows (the **hot**
  lineages). When a new job needs a row whose idle lineage is not reused, that
  lineage is copied to a host-RAM **cold store** instead of being discarded; the
  oldest/least-used idle lineage is chosen first. A later request matching a cold
  lineage restores its K/V (and the MTP draft shadow) in milliseconds — logged as
  `MP MTP prompt cache cold restore …` — instead of re-prefilling the context.
  Each rank keeps its own K/V slice in its own process; nothing large crosses the
  process pipe.
- **Thought-stripped and long conversations are handled**: a continuation whose
  client re-rendered the assistant turn (e.g. stripped the thought channel)
  restores the prompt-boundary ring snapshot and rewinds to it, so only the
  re-rendered tail re-prefills — never the document. This works even after a long
  generation shifted the SWA ring past the original prompt boundary
  (`cold restore + boundary rewind`), because the snapshot preserves that K/V.
- `cache_size` is unchanged: it remains the **per-row VRAM depth**. RAM extends
  the *number* of cached conversations (total prompt capacity = VRAM rows + RAM
  store), not a single conversation's attendable depth — the full-attention
  layers need their whole K/V prefix resident in VRAM during attention. The GPU
  VRAM allocation never grows; offload/restore only copy into preallocated
  buffers, so the cache system **cannot OOM VRAM**.

**The RAM cap is global — for the whole server, not per GPU.**
`prompt_cache_ram_limit_mb` bounds a single cold store in the parent process whose
byte counter sums **every rank's** stored slice for each lineage (master K/V +
all worker K/V slices + every rank's detached ring snapshot + the MTP shadow).
Before each offload the oldest/least-used entries are evicted until the new one
fits (`[prompt-offload] evict cold lineage …: RAM cap`); an entry larger than the
whole cap is skipped. The budget is never exceeded.

Per-process RSS is larger than `cap / num_gpus` because each process also holds
**uncapped working buffers**: the hot-row prompt-boundary ring snapshots (one
pinned full-ring copy per active slot per rank), the grow-only pinned pack
staging, the CUDA context, and (on the master) the drafter's host embedding copy.
Only the cold-store share is counted against the cap. Size the cap for the number
of conversations you want to keep warm: a Gemma-4-31B lineage at `chunk_size:
2048` costs roughly 3–3.5 GB *globally* (the fixed-size SWA ring snapshot + ring
K/V dominate, largely independent of conversation length), so e.g. 16384 MB holds
~4–5 cold lineages across the whole server. Lower the cap to reduce host RAM.

Failure-soft: a failed restore drops the entry and re-prefills from scratch; a
failed host allocation skips the offload. A job never fails because of the offload
system. `EXL2_PROMPT_OFFLOAD=0` is a debug kill switch; `EXL2_OFFLOAD_DEBUG=1`
logs the cold-match decision (match/boundary/ring origins).

### CUDA Graphs

TP decode steps are captured into CUDA graphs by default (`tp_graphs: true`,
sets `EXL2_TP_GRAPHS`). MP MTP verify windows are graphed as well. Set
`tp_graphs: false` to fall back to eager TP decode.

The MTP **drafter** graph is opt-in (`draft_model.mtp_draft_graph: true`, sets
`EXL2_MTP_DRAFT_GRAPH`). It captures the **whole draft window** into one CUDA
graph: FlashInfer paged-decode attention over the persistent MTP K/V shadows
(planned per round outside the graph) plus a GPU-resident embedding table
(+2.7 GB on the draft device), so the draft steps chain entirely on-device
with no per-step host round trips. With it enabled, Gemma-4-31B-IT measures
**~68 tok/s generation** at ~1.3k context (temperature 1, `draft_num_tokens: 3`,
4× RTX 3090 at the 200 W cap). It defaults to off; eager drafting remains the
fallback (and is used automatically if graph capture fails).

### Collective fusion (MP P2P)

The small decode/verify collectives run on a custom PCIe P2P kernel (not NCCL).
The fusion stages are **landed and evaluated**: on the 200 W-cap rig they are
throughput-neutral-to-slower (the cards are compute-limited by quantized-GEMM
dequant, not collective latency), so the optional fusion flags **stay off by
default**. The remaining big lever is the GEMM dequant path itself (see the
EXL2.5 format in the exllamav2-Fork README):

- **Warp-parallel flag/ack protocol** and a **graph-safe deferred-ack allreduce**
  (per-key double-buffered scratch) are landed unconditionally.
- `EXL2_TP_FUSE_AGNR=1` (opt-in, default off) enables a fused
  allgather+RMSNorm+residual kernel that collapses the decode block tail into one
  collective. Greedy-parity verified; throughput-neutral on the 200 W-cap rig
  (the cards are compute-limited by quantized-GEMM dequant, so latency savings
  don't move tok/s much — the GEMM dequant path is the remaining big lever).
- `EXL2_TP_ROW_REPL=1` (opt-in, default off) fuses the **o_proj** block into a single
  allreduce via an fp16 logical-order row shard (greedy-parity verified). The down
  row-parallel variant is **disabled** (`EXL2_TP_ROW_REPL_DOWN=0` default — its remap
  path has a correctness bug and an fp16 down shard is VRAM-prohibitive); down stays
  column-parallel.
- `EXL2_MTP_COST_TRACE=1` prints a per-phase MTP gather cost breakdown for profiling.

### FlashInfer

FlashInfer **>= 0.7.4 is a hard requirement** of the fork and is always enabled —
there is no disable switch. **Flash-Attention 2 is also required for now**, even
with FlashInfer: the fork's TP and dynamic-generator paths still call flash-attn
kernels directly (see the install snippet above for the prebuilt wheel).
On sm86 FlashInfer serves every attention path, including
Gemma-4's head_dim-512 full layers (paged decode wrapper in CUDA-graph mode with
a per-step re-plan, single-token decode, and prefill; verified cos 1.0 vs torch).

The only knob is the experimental plan cache:

```yml
model:
  flashinfer_plan_cache: false # EXLLAMA_FLASHINFER_PLAN_CACHE (experimental)
```

## MTP speculative decoding (Gemma-4)

The fork implements Gemma-4's native multi-token prediction with the
[google/gemma-4-31B-it-assistant](https://huggingface.co/google/gemma-4-31B-it-assistant)
drafter. The drafter cross-attends to the target's K/V (no draft cache, no
draft prefill) and runs on a single device even when the target is TP.

Download the drafter into your draft model directory (default `models/`):

```bash
hf download google/gemma-4-31B-it-assistant \
  --local-dir models/gemma-4-31B-it-assistant
```

The tested 4× RTX 3090 configuration (160k context, MP + CUDA graphs + MTP):

```yml
model:
  model_name: Gemma-4-31B-IT-EXL2-6.0BPW-HB16
  backend: exllamav2
  tensor_parallel: true
  tensor_parallel_backend: mp   # one worker per GPU (the primary tested path); or sp
  max_seq_len: 160000
  cache_size: 160000
  chunk_size: 2048
  gpu_split: [22, 22, 22, 22]   # GiB per GPU (4× 24 GB RTX 3090)
  # max_batch_size: 2           # experimental multi-batch (MP + MTP); see above
  tp_graphs: true               # whole-step TP CUDA graphs
  reasoning: true
  tool_format: gemma4

draft_model:
  draft_mode: mtp
  draft_model_name: gemma-4-31B-it-assistant
  draft_num_tokens: 3           # verify window width (3 = measured best on prose)
  draft_device: 0
```

Launch with `NCCL_P2P_LEVEL=PXB EXL2_MTP_DRAFT_GRAPH=1 python main.py` (P2P across the PCI
switch on the tested rig; the `NCCL_P2P_LEVEL` value depends on your topology — see the note
at the top of this doc). With `draft_num_tokens: 3`, `cache_size: 32768`, `chunk_size: 2048`,
`gpu_split: [22, 22, 22, 22]` and `max_batch_size: 1`, this measures **~68 tok/s generation**
on Gemma-4-31B-IT at ~1.3k context (temperature-1 sampling, 200 W-cap RTX 3090s, 2026-11-21).

Notes:

* **SP MTP** supports the full sampler (tokens are sampled from the target's
  verified logits). Sampled tokens that deviate from the drafted tokens force a
  cache rewind + recommit (fork BUG 100 fix), which guarantees corruption-free
  output but costs throughput: at temperature 1.0 expect MTP at or below plain
  decode speed at short context. MTP pays off most on greedy / low-temperature
  requests.
* **MP MTP** uses the fork's graphed-verify driver and supports the **full sampler**
  (greedy and sampled). Sampling uses probabilistic speculative acceptance (fork BUG 105):
  every emitted token is drawn from the target's verified distribution, so sampled output
  stays exactly target-autoregressive without the SP rewind-and-recommit cost. Exotic sampler
  modifiers fall back to the exact full-distribution path.
* Token healing is supported on both; banned strings and grammar filters fall
  back to plain decoding on MP.
* **Append-only prompt cache (MP MTP):** a chat continuation that strictly extends the
  previous prompt reuses the live K/V (only the new suffix is prefilled); the SWA ring is
  restored at the prior prompt boundary when needed. Prompts that diverge from the cached
  history trigger a full re-prefill (the ring bookkeeping is not rewind-safe beyond the
  verified envelope). This is why a second reply in the same conversation is fast, while a
  new/edited conversation re-prefills.
* **Short-context performance:** at ~512 tokens of context, MP MTP greedy is
  currently slower than plain MP decode (~27 vs ~37 tok/s measured) — the
  fork's per-round fixed costs (worker-pipe K/V gather/rewind, hd512
  verify-window attention) dominate. MTP pays off at longer context and on
  structured/high-acceptance prompts. This is fork-inherent, not API overhead.

### DFlash block-diffusion drafting (experimental, MP)

**Status: experimental** — first end-to-end runs verified on the tested rig; long-context and
multi-turn tool-loop validation is in progress. Requires the **mp** backend and
`max_batch_size: 1` (enforced at load).

[DFlash](https://huggingface.co/z-lab/gemma-4-31B-it-DFlash) (z-lab,
[paper](https://arxiv.org/abs/2602.06036)) drafts a whole block — one anchor token plus up to
15 mask tokens — in **one parallel pass** (block diffusion), conditioned on the target's hidden
states at six layers. Attention is FlashInfer. Unlike MTP's sequential draft steps, draft cost
is ~flat in the window width, so DFlash favors **larger windows** (`draft_num_tokens: 12`–`15`);
the default is the checkpoint's `block_size - 1` (15). Acceptance uses the same
target-distribution protocol as MP MTP (greedy and full sampler), and the append-only prompt
cache applies.

```bash
hf download z-lab/gemma-4-31B-it-DFlash \
  --local-dir models/gemma-4-31B-it-DFlash
```

```yml
draft_model:
  draft_mode: dflash            # a DFlash checkpoint is also auto-detected under 'mtp'
  draft_model_name: gemma-4-31B-it-DFlash
  draft_num_tokens: 15          # optional; default block_size - 1. Try 12-15 for throughput
  draft_device: 0
```

VRAM: the drafter adds a full fp16 lm_head copy plus its own draft K/V cache on `draft_device`
(~6.6 GB at `cache_size: 32768`, ~9.2 GB at 160k). On 24 GB cards prefer `cache_size: 32768`
unless you need the depth; 160k fits but leaves little headroom on the master rank.
**On 2-GPU splits (`gpu_split: [22, 22]`) set `draft_device: 1`** — the master's doubled weight
shard (~11.7 GB) plus the drafter stack otherwise fills GPU0 and the first prefill chunk OOMs;
the worker GPU has room for the drafter. A load-time `[dflash] WARNING` names the freest device
when the chosen placement is tight.

## Gemma-4 thinking and tool calls

Gemma-4's reasoning channel is delimited by `<|channel>thought\n` ...
`<channel|>` and is only emitted when `<|think|>` appears in the system turn.
The model's bundled `chat_template.jinja` injects it when the template variable
`enable_thinking` is true. Tool calls use the native
`<|tool_call>call:name{...}<tool_call|>` syntax, parsed by the `gemma4` tool
format (see [Tool Calling](10.-Tool-Calling.md)).

When a Gemma-4 model is detected, TabbyAPI automatically:

* defaults `tool_format` to `gemma4` (unless explicitly set),
* swaps the default reasoning tags to the thought-channel tags when
  `reasoning: true` is set without custom tags: opener `<|channel>`, closer
  `<channel|>`, with `reasoning_suppress_header: "thought\n"` to strip the
  channel header from the reasoning block. (The full opener is
  `<|channel>thought\n`, but it spans multiple tokens and the stream
  collector matches tags per chunk — the single-token opener plus header
  suppression is equivalent and robust.)
* stops generation on the end-of-turn token `<turn|>` (part of the model's HF
  EOS list, along with `<eos>` and the `<|tool_response>` guard) and on a new
  turn opener `<|turn>`. The thought-channel close tag is deliberately **not**
  a stop condition so the reasoning parser can see it.

Recommended config:

```yml
model:
  model_name: Gemma-4-31B-IT-EXL2-6.0BPW-HB16
  reasoning: true
  # Auto-detected for Gemma-4; shown here for clarity:
  reasoning_start_token: "<|channel>"
  reasoning_end_token: "<channel|>"
  reasoning_suppress_header: "thought\n"
  tool_format: gemma4
  # Clients that don't send enable_thinking themselves (e.g. OpenCode):
  force_enable_thinking: true
```

With `force_enable_thinking: false`, clients can still enable thinking
per-request via `chat_template_kwargs: {"enable_thinking": true}`. When
thinking is disabled the template appends an empty closed thought channel
(`ch<channel|>`) so the model answers directly.

### Reasoning effort

Chat completion requests accept the OAI `reasoning_effort` parameter
(`none`, `minimal`, `low`, `medium`, `high`). It is passed to the chat
template as `reasoning_effort`, and for templates gated on `enable_thinking`
(Gemma-4) it maps to the thinking switch: `none`/`minimal` disable thinking,
`low`/`medium`/`high` enable it. An explicit request-level effort overrides
the server-side `force_enable_thinking` default. Gemma-4 has no graded
thinking budget, so the three positive levels are equivalent.

```json
{"messages": [...], "reasoning_effort": "high"}
```
