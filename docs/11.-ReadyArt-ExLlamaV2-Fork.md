# ReadyArt ExLlamaV2 Fork (TP / MTP / FlashInfer)

Public repos: **[Ready-Art/TabbyAPI](https://github.com/Ready-Art/TabbyAPI)** (this integration,
branch `exl2-checkpoint`) and **[Ready-Art/Exllamav2](https://github.com/Ready-Art/Exllamav2)**
(the fork).

TabbyAPI's `exl2-checkpoint` branch supports the
[ReadyArt ExLlamaV2 fork](https://github.com/Ready-Art/Exllamav2), which adds
tensor-parallel and MTP speculative-decoding paths on top of exllamav2 0.3.2.
The fork is built and tested on **SM86 (Ampere, RTX 3090)** and requires
**flashinfer-python >= 0.7.4**.

Install the fork from source against your Torch build, e.g.:

```bash
git clone https://github.com/Ready-Art/Exllamav2
cd Exllamav2
TORCH_CUDA_ARCH_LIST="8.6" pip install -e .
pip install "flashinfer-python>=0.7.4"
```

Source installs are detected automatically and are allowed with CUDA 13 Torch
(prebuilt upstream wheels are CUDA 12 only).

## Tensor-parallel backends

`model.tensor_parallel_backend` selects the TP implementation:

| Value    | Backend                                                         |
|----------|-----------------------------------------------------------------|
| `native` | Upstream-style TP with the paged dynamic generator (batching).  |
| `sp`     | Fork single-process TP, streaming generator, batch size 1.      |
| `mp`     | Fork multiprocess TP: one worker process per GPU, batch size 1. |
| `nccl`   | Alias for `mp` on exllamav2.                                    |

**Sliding-window models (Gemma-4) must use `sp` or `mp`**: the paged TP
attention kernel has no sliding-window support. When `native` is requested for
an SWA model with TP, TabbyAPI automatically switches to `sp` and logs a
warning. Non-TP loads (single GPU / autosplit) of SWA models also use the
streaming path (batch size 1, fresh prefill per job) with the fork's
`ExLlamaV2Cache_SWA` ring cache — the paged dynamic generator's SWA ring
protocol is not verified in this integration. Non-SWA models keep the paged
dynamic generator with batching on every load mode.

The fork TP/MTP paths run **one job at a time** (`max_batch_size` is forced to
1). CFG, vision input and (for `mp`) LoRAs are not supported on these paths;
requests using them are rejected or fall back with a warning.

### CUDA Graphs

TP decode steps are captured into CUDA graphs by default (`tp_graphs: true`,
sets `EXL2_TP_GRAPHS`). MP MTP verify windows are graphed as well. Set
`tp_graphs: false` to fall back to eager TP decode.

The MTP **drafter** graph is opt-in (`draft_model.mtp_draft_graph: true`, sets
`EXL2_MTP_DRAFT_GRAPH`). It defaults to off: eager FlashInfer drafting is the
verified best state, and the graphed drafter is bandwidth-bound at long
context.

### FlashInfer

FlashInfer **>= 0.7.4 is a hard requirement** of the fork and is always enabled —
there is no disable switch. On sm86 it serves every attention path, including
Gemma-4's head_dim-512 full layers (paged decode wrapper in CUDA-graph mode with
a per-step re-plan, single-token decode, and prefill; verified cos 1.0 vs torch).

The only knob is the experimental plan cache:

```yml
model:
  flashinfer_plan_cache: false # EXLLAMA_FLASHINFER_PLAN_CACHE (experimental)
```

## MTP speculative decoding (Gemma-4)

The fork implements Gemma-4's native multi-token prediction with the
[google/gemma-4-31B-it-assistant](https://huggingface.co/google/gemma-4-31B-it-assistant)
drafter. The drafter cross-attends to the target's K/V (no draft cache, no
draft prefill) and runs on a single device even when the target is TP.

Download the drafter into your draft model directory (default `models/`):

```bash
huggingface-cli download google/gemma-4-31B-it-assistant \
  --local-dir models/gemma-4-31B-it-assistant
```

```yml
model:
  model_name: Gemma-4-31B-IT-EXL2-6.0BPW-HB16
  tensor_parallel: true
  tensor_parallel_backend: mp   # or sp
  max_seq_len: 8192
  cache_size: 8192

draft_model:
  draft_mode: mtp
  draft_model_name: gemma-4-31B-it-assistant
  draft_num_tokens: 6           # verify window width
  draft_device: 0
```

Notes:

* **SP MTP** supports the full sampler (tokens are sampled from the target's
  verified logits).
* **MP MTP** uses the fork's graphed-verify driver and is **greedy-only**.
  Non-greedy requests automatically fall back to plain MP decoding (with a
  warning), so sampling settings are always honored.
* Token healing is supported on both; banned strings and grammar filters fall
  back to plain decoding on MP.
* Every job prefills from scratch (no cross-job K/V reuse) to keep the SWA
  ring bookkeeping consistent.
* **Short-context performance:** at ~512 tokens of context, MP MTP greedy is
  currently slower than plain MP decode (~27 vs ~37 tok/s measured) — the
  fork's per-round fixed costs (worker-pipe K/V gather/rewind, torch hd512
  verify-window attention) dominate. MTP pays off at longer context and on
  structured/high-acceptance prompts. This is fork-inherent, not API overhead.

## Gemma-4 thinking and tool calls

Gemma-4's reasoning channel is delimited by `<|channel>thought\n` ...
`<channel|>` and is only emitted when `<|think|>` appears in the system turn.
The model's bundled `chat_template.jinja` injects it when the template variable
`enable_thinking` is true. Tool calls use the native
`<|tool_call>call:name{...}<tool_call|>` syntax, parsed by the `gemma4` tool
format (see [Tool Calling](10.-Tool-Calling.md)).

When a Gemma-4 model is detected, TabbyAPI automatically:

* defaults `tool_format` to `gemma4` (unless explicitly set),
* swaps the default reasoning tags to the thought-channel tags when
  `reasoning: true` is set without custom tags: opener `<|channel>`, closer
  `<channel|>`, with `reasoning_suppress_header: "thought\n"` to strip the
  channel header from the reasoning block. (The full opener is
  `<|channel>thought\n`, but it spans multiple tokens and the stream
  collector matches tags per chunk — the single-token opener plus header
  suppression is equivalent and robust.)
* stops generation on the end-of-turn token `<turn|>` (part of the model's HF
  EOS list, along with `<eos>` and the `<|tool_response>` guard) and on a new
  turn opener `<|turn>`. The thought-channel close tag is deliberately **not**
  a stop condition so the reasoning parser can see it.

Recommended config:

```yml
model:
  model_name: Gemma-4-31B-IT-EXL2-6.0BPW-HB16
  reasoning: true
  # Auto-detected for Gemma-4; shown here for clarity:
  reasoning_start_token: "<|channel>"
  reasoning_end_token: "<channel|>"
  reasoning_suppress_header: "thought\n"
  tool_format: gemma4
  # Clients that don't send enable_thinking themselves (e.g. OpenCode):
  force_enable_thinking: true
```

With `force_enable_thinking: false`, clients can still enable thinking
per-request via `chat_template_kwargs: {"enable_thinking": true}`. When
thinking is disabled the template appends an empty closed thought channel
(`ch<channel|>`) so the model answers directly.

### Reasoning effort

Chat completion requests accept the OAI `reasoning_effort` parameter
(`none`, `minimal`, `low`, `medium`, `high`). It is passed to the chat
template as `reasoning_effort`, and for templates gated on `enable_thinking`
(Gemma-4) it maps to the thinking switch: `none`/`minimal` disable thinking,
`low`/`medium`/`high` enable it. An explicit request-level effort overrides
the server-side `force_enable_thinking` default. Gemma-4 has no graded
thinking budget, so the three positive levels are equivalent.

```json
{"messages": [...], "reasoning_effort": "high"}
```

## Verified setup

Tested against
[ReadyArt/Gemma-4-31B-IT-EXL2-6.0BPW-HB16](https://huggingface.co/ReadyArt/Gemma-4-31B-IT-EXL2-6.0BPW-HB16)
on 4x RTX 3090 (sm86), Torch 2.14+cu130, FlashInfer 0.7.4. An 11-check end-to-end
suite (greedy, thinking, sampling, tool call + tool-result loop, streaming,
min_tokens, reasoning_effort none/high) runs against each mode: SP TP, MP TP,
MTP on SP and MP, CUDA graphs on/off, and non-TP autosplit. The fork's hd512
FlashInfer kernels are parity-checked vs torch (cos 1.0), and graph-mode greedy
decode matches eager token-for-token.
