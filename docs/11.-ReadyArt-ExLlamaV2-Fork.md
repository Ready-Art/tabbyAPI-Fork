# ReadyArt ExLlamaV2 Fork (TP / MTP / FlashInfer)

Public repos: **[Ready-Art/tabbyAPI-Fork](https://github.com/Ready-Art/tabbyAPI-Fork)** (this integration,
branch `ReadyArt`) and **[Ready-Art/exllamav2-Fork](https://github.com/Ready-Art/exllamav2-Fork)**
(the fork).

TabbyAPI's `ReadyArt` branch supports the
[ReadyArt ExLlamaV2 fork](https://github.com/Ready-Art/exllamav2-Fork), which adds
tensor-parallel and MTP speculative-decoding paths on top of exllamav2 0.3.2.
The fork is built and tested on **SM86 (Ampere, RTX 3090)** and requires
**flashinfer-python >= 0.7.4** plus **Flash-Attention 2 (required for now, even with FlashInfer)**.

Install the fork from source against your Torch build (tested: Python 3.12.15, torch 2.15.0+cu132,
CUDA toolkit 13.5 with `nvcc` on `PATH`):

```bash
# uv manages Python 3.12 itself (https://docs.astral.sh/uv/getting-started/installation/)
uv python install 3.12
uv venv venv --python 3.12 && source venv/bin/activate

# torch first — the fork's setup.py compiles its CUDA extension against the installed torch
uv pip install torch==2.15.0+cu132 --index-url https://download.pytorch.org/whl/cu132

git clone https://github.com/Ready-Art/exllamav2-Fork
cd exllamav2-Fork
uv pip install -r requirements.txt
TORCH_CUDA_ARCH_LIST="8.6" uv pip install -e . --no-build-isolation
flashinfer download-kernels

# Flash-Attention 2 — required for now even with FlashInfer (TP / dynamic-generator paths).
# Wheel for Python 3.12 / torch 2.15 / CUDA 13.2; other combinations:
# https://github.com/mjun0812/flash-attention-prebuild-wheels/releases
uv pip install "https://github.com/mjun0812/flash-attention-prebuild-wheels/releases/download/v1.5.0/flash_attn-2.8.3+cu132torch2.15-cp312-cp312-linux_x86_64.whl"
```

Source installs are detected automatically and are allowed with CUDA 13 Torch
(prebuilt upstream wheels are CUDA 12 only).

**CUDA allocator:** the fork TP backends (`sp`/`mp`) force PyTorch's **native**
caching allocator. `cudaMallocAsync` corrupts the fork's whole-step CUDA-graph
replay (token-level garbage under sampling) and breaks MP's IPC worker pipes, so
TabbyAPI overrides `PYTORCH_CUDA_ALLOC_CONF` to `backend:native` for these backends
even if it is preset in your environment. No action needed; do not force
`cudaMallocAsync` back on for the fork TP path.

## Tensor-parallel backends

`model.tensor_parallel_backend` selects the TP implementation:

| Value    | Backend                                                         |
|----------|-----------------------------------------------------------------|
| `native` | Upstream-style TP with the paged dynamic generator (batching).  |
| `sp`     | Fork single-process TP, streaming generator, batch size 1.      |
| `mp`     | Fork multiprocess TP: one worker process per GPU, batch size 1. |
| `nccl`   | Alias for `mp` on exllamav2.                                    |

**Sliding-window models (Gemma-4) must use `sp` or `mp`**: the paged TP
attention kernel has no sliding-window support. When `native` is requested for
an SWA model with TP, TabbyAPI automatically switches to `sp` and logs a
warning. Non-TP loads (single GPU / autosplit) of SWA models also use the
streaming path (batch size 1, fresh prefill per job) with the fork's
`ExLlamaV2Cache_SWA` ring cache — the paged dynamic generator's SWA ring
protocol is not verified in this integration. Non-SWA models keep the paged
dynamic generator with batching on every load mode.

The fork TP/MTP paths run **one job at a time** (`max_batch_size` is forced to
1). CFG, vision input and (for `mp`) LoRAs are not supported on these paths;
requests using them are rejected or fall back with a warning.

### CUDA Graphs

TP decode steps are captured into CUDA graphs by default (`tp_graphs: true`,
sets `EXL2_TP_GRAPHS`). MP MTP verify windows are graphed as well — including
per-row hidden-state extraction (the bonus-eliminated protocol) and a
single-pass FlashInfer paged-prefill attention kernel per layer, re-planned
outside the graph each step (fixed-buffer graph mode). Set `tp_graphs: false`
to fall back to eager TP decode.

The MTP **drafter** graph is opt-in (`draft_model.mtp_draft_graph: true`, sets
`EXL2_MTP_DRAFT_GRAPH`). It defaults to off: eager FlashInfer drafting is the
verified best state, and the graphed drafter is bandwidth-bound at long
context.

### FlashInfer

FlashInfer **>= 0.7.4 is a hard requirement** of the fork and is always enabled —
there is no disable switch. **Flash-Attention 2 is also required for now**, even
with FlashInfer: the fork's TP and dynamic-generator paths still call flash-attn
kernels directly (see the install snippet above for the prebuilt wheel).
On sm86 FlashInfer serves every attention path, including
Gemma-4's head_dim-512 full layers (paged decode wrapper in CUDA-graph mode with
a per-step re-plan, single-token decode, and prefill; verified cos 1.0 vs torch).

The only knob is the experimental plan cache:

```yml
model:
  flashinfer_plan_cache: false # EXLLAMA_FLASHINFER_PLAN_CACHE (experimental)
```

## MTP speculative decoding (Gemma-4)

The fork implements Gemma-4's native multi-token prediction with the
[google/gemma-4-31B-it-assistant](https://huggingface.co/google/gemma-4-31B-it-assistant)
drafter. The drafter cross-attends to the target's K/V (no draft cache, no
draft prefill) and runs on a single device even when the target is TP.

Download the drafter into your draft model directory (default `models/`):

```bash
hf download google/gemma-4-31B-it-assistant \
  --local-dir models/gemma-4-31B-it-assistant
```

```yml
model:
  model_name: Gemma-4-31B-IT-EXL2-6.0BPW-HB16
  tensor_parallel: true
  tensor_parallel_backend: mp   # or sp
  max_seq_len: 8192
  cache_size: 8192

draft_model:
  draft_mode: mtp
  draft_model_name: gemma-4-31B-it-assistant
  draft_num_tokens: 3           # verify window width (3 = measured MP sweet spot)
  draft_device: 0
```

Notes:

* **Both SP and MP MTP support the full sampler.** Tokens are decided at round
  time by **probabilistic speculative acceptance** against the target's verified
  logits: a draft is accepted with probability `p_target(draft)`, and on
  rejection the replacement is drawn from the residual distribution — no resync
  forward, no rewind-and-recommit. The emitted distribution is exactly
  target-autoregressive at any temperature; draft quality only affects the
  acceptance rate. Temperature-1.0 MP MTP measures ~40 tok/s at ~1.3k context
  (window 3, 4× 3090).
* **MP MTP rounds cost one target forward.** The bonus token decided by a round
  becomes row 0 of the next verify window (W+1 rows), which writes its K/V and
  returns its logits and hidden state — the separate bonus forward is gone
  (fork `EXL2_MTP_BONUS_ELIM`, default on). The verify window is CUDA-graphed
  with a single-pass FlashInfer paged-prefill kernel per layer (KV read once for
  all rows) and per-row hidden-state extraction.
* **Window width:** `draft_num_tokens: 3` is the measured sweet spot on MP
  (wider windows grow verify/draft cost faster than acceptance).
* Token healing is supported on both; banned strings and grammar filters fall
  back to plain decoding on MP.
* **Append-only prompt cache (MP MTP):** chat continuations reuse the previous
  job's K/V and prefill only the new tokens — an 80k-context second reply
  prefills just the new turn instead of reprocessing the whole conversation
  (log: `MP MTP prompt cache hit: reusing N tokens, prefilling M new`). Reuse
  requires the new prompt to strictly EXTEND the cached token sequence; the
  few-token tail left by a mid-round stop is trimmed with a distributed rewind
  (safe: the 1280-deep SWA ring still holds every retained position). Large
  rewinds are not ring-safe, so edited/re-rendered history (e.g. a client that
  strips thought channels from history) falls back to a full reset + re-prefill;
  misses are logged with the reason and first divergent token.
  When the divergence is at the previous prompt's end — the usual case for
  clients that strip thought channels from history (the latest assistant turn
  is re-rendered without thoughts) — the fork restores an exact SWA-ring
  snapshot taken at the end of that prompt's prefill (`MP MTP prompt cache
  restore: rewound to prompt boundary N`) and prefills only the last rendered
  turn plus the new message. The snapshot is refreshed at every prompt
  boundary, so from the second reply onward each turn prefills a constant-size
  tail regardless of conversation length. The ring snapshot costs ~262 MB of
  VRAM per GPU (Gemma-4, 4-way split); one buffer, replaced per job.
* **Client disconnects abort the job**, including mid-prefill: every rank stops
  at the same chunk boundary (a collective abort flag), so a disconnected 80k
  prompt no longer keeps processing in the background.
* **Long-prompt prefill** is dramatically faster than earlier builds: hd512
  prefill runs on the cuDNN fused engine with persistent per-geometry wrappers,
  sliding layers on FlashInfer's windowed kernel. `EXL2_PREFILL_TRACE` (default
  on) prints `[prefill] N/total (ms/chunk)` progress on long loads.
* **Short-context performance:** MP MTP still carries per-round fixed costs
  (drafter window, K/V gather, acceptance) that plain decode doesn't pay; the
  gap is much smaller than before (bonus elimination + packed gather +
  single-pass verify cut the round from ~76 ms to ~57 ms). MTP pays off most at
  longer context and on structured/high-acceptance prompts. Fork-inherent, not
  API overhead.

### Fork performance controls (environment variables)

Set in the server environment; defaults are the verified best state.

| Variable | Default | Effect |
|---|---|---|
| `EXL2_TP_SEQPAR` | `1` | MP sequence-parallel hidden-sharded residual (collective-volume win, prefill/long context). `0` = replicated residual. |
| `EXL2_MTP_BONUS_ELIM` | `1` | One target forward per MTP round. `0` = legacy verify+bonus. |
| `EXL2_VERIFY_PREFILL` | `1` | Single-pass graphed verify kernel. `0` = per-row decode kernels. |
| `EXL2_PREFILL_CUDNN` | `1` | cuDNN engine for hd512 eager prefill (probed, auto-fallback). `0` = fa2 only. |
| `EXL2_MTP_WARMUP` | `1` | FlashInfer JIT at server load instead of first request. |
| `EXL2_PREFILL_TRACE` | `1` | Per-chunk prefill progress logging. |
| `EXL2_MTP_DRAFT_GRAPH` | `0` | Opt-in drafter graph (eager FlashInfer is the verified best). |

## Gemma-4 thinking and tool calls

Gemma-4's reasoning channel is delimited by `<|channel>thought\n` ...
`<channel|>` and is only emitted when `<|think|>` appears in the system turn.
The model's bundled `chat_template.jinja` injects it when the template variable
`enable_thinking` is true. Tool calls use the native
`<|tool_call>call:name{...}<tool_call|>` syntax, parsed by the `gemma4` tool
format (see [Tool Calling](10.-Tool-Calling.md)).

When a Gemma-4 model is detected, TabbyAPI automatically:

* defaults `tool_format` to `gemma4` (unless explicitly set),
* swaps the default reasoning tags to the thought-channel tags when
  `reasoning: true` is set without custom tags: opener `<|channel>`, closer
  `<channel|>`, with `reasoning_suppress_header: "thought\n"` to strip the
  channel header from the reasoning block. (The full opener is
  `<|channel>thought\n`, but it spans multiple tokens and the stream
  collector matches tags per chunk — the single-token opener plus header
  suppression is equivalent and robust.)
* stops generation on the end-of-turn token `<turn|>` (part of the model's HF
  EOS list, along with `<eos>` and the `<|tool_response>` guard) and on a new
  turn opener `<|turn>`. The thought-channel close tag is deliberately **not**
  a stop condition so the reasoning parser can see it.

Recommended config:

```yml
model:
  model_name: Gemma-4-31B-IT-EXL2-6.0BPW-HB16
  reasoning: true
  # Auto-detected for Gemma-4; shown here for clarity:
  reasoning_start_token: "<|channel>"
  reasoning_end_token: "<channel|>"
  reasoning_suppress_header: "thought\n"
  tool_format: gemma4
  # Clients that don't send enable_thinking themselves (e.g. OpenCode):
  force_enable_thinking: true
```

With `force_enable_thinking: false`, clients can still enable thinking
per-request via `chat_template_kwargs: {"enable_thinking": true}`. When
thinking is disabled the template appends an empty closed thought channel
(`ch<channel|>`) so the model answers directly.

### Reasoning effort

Chat completion requests accept the OAI `reasoning_effort` parameter
(`none`, `minimal`, `low`, `medium`, `high`). It is passed to the chat
template as `reasoning_effort`, and for templates gated on `enable_thinking`
(Gemma-4) it maps to the thinking switch: `none`/`minimal` disable thinking,
`low`/`medium`/`high` enable it. An explicit request-level effort overrides
the server-side `force_enable_thinking` default. Gemma-4 has no graded
thinking budget, so the three positive levels are equivalent.

```json
{"messages": [...], "reasoning_effort": "high"}
```

## Verified setup

Tested against
[ReadyArt/Gemma-4-31B-IT-EXL2-6.0BPW-HB16](https://huggingface.co/ReadyArt/Gemma-4-31B-IT-EXL2-6.0BPW-HB16)
on 4x RTX 3090 (sm86), Torch 2.14+cu130, FlashInfer 0.7.4. The install and kernel
parity checks were re-verified on Python 3.12.15, Torch 2.15.0+cu132, CUDA toolkit
13.5, FlashInfer 0.7.4 (cu130 jit-cache kernels) and flash-attn 2.8.3
(cu132torch2.15 prebuilt wheel), followed by full-length generation checks on that
stack with a 160000-token SWA cache: SP MTP at temperature 1.0 / top_p 0.92, MP MTP
greedy, and MP sampling (plain-MP fallback) all produced coherent, corruption-free
multi-thousand-token stories (fork BUG 100 sampling-desync and BUG 101 MP NCCL
all_gather contiguity fixes). An 11-check end-to-end
suite (greedy, thinking, sampling, tool call + tool-result loop, streaming,
min_tokens, reasoning_effort none/high) runs against each mode: SP TP, MP TP,
MTP on SP and MP, CUDA graphs on/off, and non-TP autosplit. The fork's hd512
FlashInfer kernels are parity-checked vs torch (cos 1.0), and graph-mode greedy
decode matches eager token-for-token.

**2026-11-20 re-verification** (same hardware, 160k SWA cache): MP MTP at
temperature 1.0 / top_p 0.92, window 3, ~1.3k context → **40.2 tok/s** with
coherent thinking-block output; the sequence-parallel residual path
(`EXL2_TP_SEQPAR=1`, now default) is greedy-parity with the replicated path
(30-token text identical, prefill logits cos 0.999978); long-prompt prefill
vastly improved after the cuDNN hd512 prefill switch (user-confirmed on a 75k
prompt: ~650 tok/s prompt processing, **40 tok/s generation at 75k context**);
client disconnect aborts mid-prefill on all ranks; the append-only prompt cache
with rolling SWA-ring restore is user-confirmed working — second and later
replying turns restore to the previous prompt boundary and prefill only the
re-rendered tail (thought-stripping clients included).
